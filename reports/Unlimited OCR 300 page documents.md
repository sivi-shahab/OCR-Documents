# Split 300-page PDFs into independent page jobs

To OCR a 300+ page document with Unlimited-OCR, send each page as its own vLLM request and run the document as an asynchronous, checkpointed job. Do not use one long "multi-page" pass. The model's "unlimited" name refers to output length, not input. Each page costs **273 prefill tokens** in Base mode, so **a 300-page document needs about 81,900 prompt tokens against a hard 32,768-token context**. The paper itself admits the model "cannot achieve truly unlimited parsing under a finite context length" ([paper p.11 §7](https://arxiv.org/abs/2606.23050)). The REST API in this repo fails on such a document in several ways at once. It rejects anything over **200 pages** or **50 MB** with HTTP 413. Its `whole_document` strategy cannot fit the context. Its default `per_page` strategy runs as a single synchronous HTTP call that holds every rendered page in RAM, uses only 8 concurrent requests, and throws away all completed pages if any one page fails. The fix is mostly architectural: `POST` a job, render pages in a streaming CPU pool, fan out one-page requests to a well-saturated vLLM, record per-page status and QC flags, retry bad pages, and reassemble with page provenance. Model settings matter less but still matter. Use single-page (Gundam) mode with the 128-token n-gram window, cap `max_tokens` with a `finish_reason` check, and raise in-flight concurrency from 8 to roughly 64–256. No one has measured throughput on this deployment's GPU yet, so every wall-clock figure below is an estimate to verify with a benchmark.

## The 32K context caps one request at roughly 11 dense pages, not 300

Unlimited-OCR is Baidu's continued training of DeepSeek-OCR. It uses the same DeepEncoder and a **3B-total / ~0.5B-active MoE decoder**, with every attention layer replaced by Reference Sliding Window Attention (R-SWA). With R-SWA, each output token attends to all visual tokens and prompt tokens but only the previous 128 output tokens ([paper p.5 §3.2](https://arxiv.org/abs/2606.23050)). This bounds the KV cache during *generation*, but the prefill still grows with every page. Training used a **32K maximum sequence length** ([paper p.8 §4.1–4.2](https://arxiv.org/abs/2606.23050)), and the compose file serves the model with `--max-model-len=32768` ([api/docker-compose.yml:14](../api/docker-compose.yml)).

The per-page cost comes from vLLM's processor code. A Base-mode (1024×1024) page is a 272-token global view plus one separator, or **273 tokens**. A Gundam (crop) page adds 640×640 tiles and can reach **3,553 tokens** at the maximum 4×8 grid ([vLLM image `unlimited_ocr.py:135-166`](file:///usr/local/lib/python3.12/dist-packages/vllm/model_executor/models/unlimited_ocr.py)). Multi-page requests are Base-only: vLLM falls back to non-crop mode whenever more than one image is sent ([vLLM image `unlimited_ocr.py:208-216`](file:///usr/local/lib/python3.12/dist-packages/vllm/model_executor/models/unlimited_ocr.py)), and the README says "Multi page / PDF only uses base" ([README.md:80-100](../README.md)). Prefill alone therefore fills the window at about **120 pages**, with no room left for output.

Output is the tighter constraint. The paper assumes about a 1:10 visual-to-text compression, so that "10K visual tokens (roughly 20-30 pages) demand an output length of 100k+ tokens" ([paper p.6 §3.4](https://arxiv.org/abs/2606.23050)). That works out to about **2,700 output tokens per dense page**. vLLM's R-SWA is implemented as "full KV cache + custom mask" on FlexAttention ([vLLM image `unlimited_ocr.py:21-32`](file:///usr/local/lib/python3.12/dist-packages/vllm/model_executor/models/unlimited_ocr.py)), so under vLLM every generated token also counts against the 32K. Solving 273·N + 2,700·N ≤ 32,768 gives **about 11 dense pages per request**. That is an estimate; text-light pages allow more. The constant-memory ring buffer exists only in the Transformers and SGLang paths, so this repo's vLLM stack gets none of R-SWA's memory benefit.

Quality also falls as requests get longer. On the paper's in-house book set, edit distance rises from **0.036 at 2 pages to 0.107 at 40+ pages**, and Distinct-35 drops from 99.87% to 96.90% ([paper p.11 Table 3](https://arxiv.org/abs/2606.23050)). The authors attribute the errors to small text that Base resolution cannot read ([paper p.10 §5.4](https://arxiv.org/abs/2606.23050)), which is an argument against Base mode for dense pages. Page boundaries in multi-page output are also unreliable. Upstream users report that `<page>` separators go missing or land in the wrong place even at 2–3 pages, more often under vLLM ([issue #107](https://github.com/baidu/Unlimited-OCR/issues/107)). Neither Baidu nor the vLLM recipe states a maximum page count or a chunk size for 100+ page books ([vLLM recipe](https://recipes.vllm.ai/baidu/Unlimited-OCR); [HF card](https://huggingface.co/baidu/Unlimited-OCR)). The "128K model" and "prefill pool" the paper proposes as future work are unreleased. Small multi-page chunks of about 5–10 pages remain an option when cross-page reading order matters more than page attribution, but one page per request should be the default.

## Eleven ways the current API and `infer.py` break at 300 pages

With default settings the REST API never reaches the model. Raising the limits only moves the failure deeper into the code. The table maps each failure to its location in the code.

| # | Failure at 300+ pages | Where | Consequence |
|---|---|---|---|
| 1 | `max_pdf_pages=200` | [config.py:26](../api/app/core/config.py), [pdf_renderer.py:32-35](../api/app/infrastructure/pdf_renderer.py) | Immediate 413 |
| 2 | `max_upload_mb=50`; whole upload joined in memory | [dependencies.py:16-27](../api/app/api/dependencies.py) | Large scanned PDFs rejected |
| 3 | `whole_document` sends all pages in one request | [ocr_service.py:32-33](../api/app/services/ocr_service.py) | 81.9K prompt + 8,192 `max_tokens` > 32,768, so vLLM returns 400 and the API returns 502 |
| 4 | Even within context, `whole_document` output is capped at 8,192 tokens and `<page>` is not parsed | [vllm_engine.py:44-76](../api/app/infrastructure/vllm_engine.py), [parser.py:23-42](../api/app/domain/parser.py) | About 3 dense pages of text survive; one `page: null` blob |
| 5 | Every page rendered to PNG in memory before any OCR starts | [pdf_renderer.py:36-38](../api/app/infrastructure/pdf_renderer.py), [ocr_service.py:31](../api/app/services/ocr_service.py) | High peak RSS, then +33% again as base64; GPU idle during rendering |
| 6 | Single synchronous `POST /v1/ocr/pdf`, no job ID, progress or streaming | [routes.py:44-62](../api/app/api/routes.py) | Client and proxy timeouts; work continues after a client disconnect |

| 8 | Process-wide `Semaphore(8)`, `max_connections=16` | [ocr_service.py:24,43-46](../api/app/services/ocr_service.py), [main.py:42-47](../api/app/main.py) | GPU under-filled; one big job blocks all other users |
| 9 | `finish_reason` never checked | [vllm_engine.py:71-76](../api/app/infrastructure/vllm_engine.py) | Truncated or looping pages pass as success |
| 10 | Single uvicorn process doing CPU-bound rendering | [Dockerfile:17](../api/Dockerfile) | Rendering competes with request handling |
| 11 | `infer.py`: no resume, failed pages become empty `.md` files, temp directory leaked, no merged output | [infer.py:155,226-227,240-283](../infer.py), [issue #17](https://github.com/baidu/Unlimited-OCR/issues/17) | A crash at page 280 means starting over |

Three items dominate. First, row 7 makes failure all-or-nothing, and with hundreds of pages per job, some page *will* fail. Upstream users measured looping on **about 1.2% of Base-mode pages and 0.24% of Gundam pages**, and the test page only degenerated at budgets of 8,192 tokens or more ([issue #55](https://github.com/baidu/Unlimited-OCR/issues/55)). At those rates a 300-page Base-mode job expects about three looping pages. Second, row 9 means those loops silently burn the full 8,192-token budget, which also sets the worst-case tail latency. Third, row 8 leaves most of vLLM's batching capacity unused. The paper's 5,580 tokens/s figure was measured at **512 concurrency** ([paper p.10](https://arxiv.org/abs/2606.23050)), while the API never has more than 8 requests in flight. `infer.py` degrades more gracefully because it writes per-page files and retries 5 times ([infer.py:205-227](../infer.py)), but it has no resume and turns failures into silent empty pages.

## Gundam per page, capped tokens and an explicit finish check

**Mode.** Use single-image requests with the prompt `"<image>document parsing."` and `window_size=128`, which is what the API's `per_page` path already sends ([vllm_engine.py:10-12,44-58](../api/app/infrastructure/vllm_engine.py)). vLLM then picks Gundam (crop) mode automatically. Choose Gundam over Base for large documents. It reads small print that Base resolution misses (the paper's own explanation for multi-page errors), and in the issue #55 measurements it looped about five times less often. The cost is prefill: up to 3,553 tokens per page instead of 273. That is cheap compared with roughly 2,700 decoded tokens on a dense page, because prefill is batched and parallel while decode is sequential. Keep the n-gram logits processor on with `ngram_size=35`. The official recipe calls it "required" because "without it long documents loop on `<|det|>` coordinate tokens", and it also specifies `temperature=0` and `skip_special_tokens=False` ([vLLM recipe](https://recipes.vllm.ai/baidu/Unlimited-OCR)). Reserve `window_size=1024` and "Multi page parsing." for the optional multi-page chunk path.

**Resolution.** The API renders at 200 DPI, while `infer.py` and the README use 300 DPI ([config.py:27](../api/app/core/config.py); [infer.py:26](../infer.py); [README.md:94-130](../README.md)). Keep 200 DPI as the default, and re-render at 300 DPI as an escalation for pages flagged as sparse or garbled. Two reasons support this. Research on other VLMs finds little accuracy gain above about 144–200 DPI ([arXiv 2609.29933](https://arxiv.org/pdf/2609.29933)), and AWS's rule of thumb that 8-point text at 150 DPI meets its 15 px minimum puts 200 DPI comfortably above that floor ([AWS Textract quotas](https://docs.aws.amazon.com/textract/latest/dg/limits-document.html)). Gundam's tile count depends on image size, so DPI changes both accuracy and prefill cost. Nobody has measured the trade-off for this model, so benchmark 150, 200 and 300 DPI on a sample of your own corpus before fixing the value.

**Output budget.** A budget of 8,192 tokens is roughly 3x the dense-page average, and the loops reported in issue #55 only appeared at that budget or higher. Set the first-pass `max_tokens` to about **6,144**, and treat any `finish_reason != "stop"` as a failure that enters the retry ladder. olmOCR uses the same rule: a result is invalid if `finish_reason != "stop"` ([olmOCR pipeline.py](https://raw.githubusercontent.com/allenai/olmocr/main/olmocr/pipeline.py)). If a truncated output is *not* repetitive, the page is genuinely dense, so retry it at 8,192. If it is repetitive, follow olmOCR's approach and retry with a small temperature bump. olmOCR raises temperature from 0.1 to 1.0 across 8 attempts because "higher temperature helps with repetition". If that also fails, re-render at a different DPI and finally fall back to the PDF text layer ([olmOCR pipeline.py](https://raw.githubusercontent.com/allenai/olmocr/main/olmocr/pipeline.py)). The value 6,144 is a judgement call; adjust it to your corpus's measured output-length distribution.

## Tune vLLM for many short sequences, not one long one

Per-page requests change the serving profile. A worst-case Gundam page needs about 3,553 prompt tokens plus 8,192 output tokens, roughly 12K, so the context window is no longer the constraint. **Concurrency** is. Keep the recipe's `--no-enable-prefix-caching` and `--mm-processor-cache-gb=0`, which the compose file already sets and which the DeepSeek-OCR recipe justifies because "OCR workloads don't benefit much from them, and they add hashing overhead" ([vLLM DeepSeek-OCR recipe](https://docs.vllm.ai/projects/recipes/en/latest/DeepSeek/DeepSeek-OCR.html)). The settings below are a starting point to measure against, not tested values.

| Setting | Today | Recommended start | Why |
|---|---|---|---|
| `--max-model-len` | 32768 | 16384 for per-page-only deployments | Worst case is about 12K; this tightens memory profiling. Keep 32768 if multi-page chunks are served from the same instance |
| `--max-num-batched-tokens` | default | ≥ 8192, and above 3,553 | Docs advise >8192 for throughput on small models; a single image's tokens must fit in it ([vLLM optimization](https://docs.vllm.ai/en/latest/configuration/optimization.html); [encoder cache](https://docs.vllm.ai/en/v0.9.1/api/vllm/v1/core/encoder_cache_manager.html)) |
| `--max-num-seqs` | default | Step 64, then 128, then 256 | Stop raising it once preemption counters climb ([vLLM optimization](https://docs.vllm.ai/en/latest/configuration/optimization.html)) |
| `--gpu-memory-utilization` | default 0.9 | 0.85–0.92 | Room for KV cache and CUDA graphs |
| `--limit-mm-per-prompt` | unset | `{"image":1}` for per-page instances | Makes memory profiling reserve the right encoder budget ([conserving memory](https://docs.vllm.ai/en/latest/configuration/conserving_memory.html)) |
| Multi-GPU | 1 GPU | One replica per GPU (data parallel), not tensor parallel | A 3B model fits on one GPU; TP sync overhead buys nothing ([vLLM optimization](https://docs.vllm.ai/en/latest/configuration/optimization.html)) |
| API `page_concurrency` / `max_connections` | 8 / 16 | At or slightly above effective `max_num_seqs` | Keep the batch full without excess queueing |
| Client read timeout | 1200 s per phase | Size to `max_tokens` ÷ per-sequence decode rate under load | Decode can fall to 20–50 tok/s per sequence when the batch is full |

Run with stats logging on and watch KV-cache usage, the waiting queue and the preemption counter. vLLM's default response to KV exhaustion is RECOMPUTE, which silently wastes work ([vLLM optimization](https://docs.vllm.ai/en/latest/configuration/optimization.html)). CPU is the other hidden bottleneck. Each vLLM API server loads media with 8 threads, and the docs recommend at least 2 + N physical cores for N GPUs ([vLLM optimization](https://docs.vllm.ai/en/latest/configuration/optimization.html)). In the FastAPI service, PDF rasterisation and base64 encoding compete for those same cores. One third-party OCR deployment gained 37% throughput just by removing CPU thread contention during preprocessing ([Friendli](https://friendli.ai/models/aijiag/MinerU2.5-Pro-2605-0.6B)), though that is a weak, vendor-reported source.

For planning, take the paper's **5,580 tokens/s at 512 concurrency** in Base mode ([paper p.10](https://arxiv.org/abs/2606.23050)) and multiply 300 pages by about 2,700 tokens. That gives about 810K output tokens, or **roughly 2.5 minutes of pure decode in the ideal case**. Gundam prefill, lower practical concurrency, retries and the slowest page will push real wall time higher. For comparison, published small OCR VLMs on one A100 reach about 1–2 pages/s end to end ([PaddleOCR-VL report](https://arxiv.org/html/2510.14528); [MinerU2.5](https://arxiv.org/html/2509.22186)), which would put 300 pages at 2.5–5 minutes. At today's concurrency of 8, the GPU sits largely idle and the job takes many times longer. Measure with `vllm bench serve` on your hardware before quoting SLAs.

## Build the large-job path as submit, fan out, checkpoint, reassemble

Every large-document system examined uses the same shape. A job is submitted and assigned an ID, its units of work are processed independently with per-unit completion recorded durably, the client polls or is notified, and results are fetched in pages. Azure caps one analysis at 2,000 pages, AWS Textract at 3,000 and Google Document AI batch at 500 pages ([Azure limits](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/service-limits); [AWS quotas](https://docs.aws.amazon.com/textract/latest/dg/limits-document.html); [Google limits](https://docs.cloud.google.com/document-ai/limits)). olmOCR imposes no per-document cap and instead shards work into groups of about 500 pages, using only lock and done-flag files ([olmOCR work_queue.py](https://raw.githubusercontent.com/allenai/olmocr/main/olmocr/work_queue.py)). Keep the existing synchronous `POST /v1/ocr/pdf` for small documents, for example up to 20 pages. Add the asynchronous job API below for everything else, with configurable caps of about 2,000 pages and 500 MB.

| Endpoint | Behaviour |
|---|---|
| `POST /v1/ocr/jobs` | Multipart upload or source URI, with an `Idempotency-Key` or SHA-256 of the file. Stores the PDF, counts pages and returns `202 {job_id, pages_total}`. A resubmitted identical file returns the existing job |
| `GET /v1/ocr/jobs/{id}` | `{status, pages_total, pages_done, pages_failed, pages_flagged}`. Clients poll no faster than every 2 s, as Azure advises ([Azure limits](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/service-limits)) |
| `GET /v1/ocr/jobs/{id}/events` | Server-Sent Events, one event per page completion |
| `GET /v1/ocr/jobs/{id}/pages?offset=&limit=` and `/pages/{n}` | Per-page markdown, optional raw output, QC flags; readable while the job is still running |
| `GET /v1/ocr/jobs/{id}/result.md` and `result.json` | Assembled document streamed from storage. The JSON carries `[start, end, page]` provenance spans, as in olmOCR's `pdf_page_numbers` ([olmOCR pipeline.py](https://raw.githubusercontent.com/allenai/olmocr/main/olmocr/pipeline.py)) |
| `DELETE /v1/ocr/jobs/{id}` | Cancels pending pages |
| Webhook (optional) | HMAC-signed POST on completion |

Behind these endpoints, a `pages` table stores `(job_id, page_no, status, attempts, dpi, finish_reason, output_tokens, qc_flags, output_key)`. Status moves through `pending → rendering → ocr → done | fallback | failed`. On a single GPU node, a SQLite or Postgres table plus an in-process asyncio dispatcher is enough. On multiple nodes, Celery with `acks_late` and a visibility timeout longer than one page group's runtime fits, but tasks must be idempotent ([Celery Redis docs](https://docs.celeryq.dev/en/v5.0.0/getting-started/brokers/redis.html)). Key page outputs by `(pdf_sha256, page_no, model_revision, prompt_version, dpi)`. Resuming then just means re-enqueuing pages that are not done, and re-submitting a document is a cache hit. Pin the model revision as the compose file already does with `07dea832`, because a later upstream commit renamed `model_type` and broke the vLLM image ([api/README.md:18-20](../api/README.md)).

Rendering moves into a separate process pool. Each worker opens the PDF itself, renders its own page range and writes PNGs to `{job_id}/pages/{n:05d}.png` on disk or in object storage. Rendering uses processes rather than threads because PDFium is not thread-safe, and pypdfium2's maintainers dropped built-in multiprocess rendering because shipping bitmaps back to a parent process cost memory without any speed gain ([pypdfium2 docs](https://pypdfium2.readthedocs.io/en/stable/python_api.html); [changelog](https://pypdfium2.readthedocs.io/en/stable/changelog.html)). The OCR dispatcher consumes rendered pages as they appear, so inference starts after the first page instead of the 300th. This mirrors PaddleOCR-VL's queue-connected render and inference stages ([PaddleOCR-VL report](https://arxiv.org/html/2510.14528)). Replace the global semaphore with a global in-flight cap matched to vLLM, plus a per-job fair share, so a 300-page job cannot starve a one-page request. A cheap pre-pass extracts each page's embedded text layer. That gives a fallback for pages that exhaust their retries (olmOCR's `pdftotext` fallback, flagged `is_fallback`), and lets born-digital pages optionally skip the VLM, as Marker's fast path does ([Marker README](https://github.com/datalab-to/marker)).

Quality control runs per page. A page is flagged `truncated` when `finish_reason == "length"`, `repetition` when its compression ratio or top n-gram frequency is high, `empty` when it has ink but no text, and `text_layer_disagreement` when it diverges from the embedded text. Failed pages climb a bounded escalation ladder: retry at a higher token budget or slightly higher temperature, then re-render at 300 DPI, then fall back to the text layer, then mark the page `failed`. The job still completes as partially successful. Adopt olmOCR's document-level budget, which flags or fails a document whose fallback ratio exceeds 1/250 ([olmOCR README](https://github.com/allenai/olmocr)). Reassembly concatenates pages in order with `<!-- page: n -->` anchors. It then makes one pass over each adjacent page pair to strip running headers and footers, rejoin hyphenated words and broken paragraphs, and merge tables split across pages. Merge a table when the two halves have matching column counts and the second repeats the header row. Marker and LlamaParse offer the same kind of continued-table merging ([Marker README](https://github.com/datalab-to/marker); [LlamaParse tables](https://developers.llamaindex.ai/llamaparse/parse/features/tables/)). None of these heuristics has published accuracy numbers, so sample flagged pages plus 1–2% of clean pages for human review.

## Conclusion

The paper's long-horizon framing points the wrong way for this deployment. Under vLLM, R-SWA is only an attention mask over a full KV cache. Its memory advantage disappears, and one-shot book parsing collides with the 32K window at about a dozen dense pages. For large documents, Unlimited-OCR is therefore best treated as a fast, accurate *page* model, and its "unlimited" capability as irrelevant. The engineering effort belongs in job orchestration rather than in prompts: durable per-page state, isolated failures, streaming rendering, and enough concurrency to fill the GPU. These are the same patterns olmOCR and the cloud OCR APIs converged on, so the design carries little novelty risk.

Three open questions should be settled with measurements before committing to numbers. The first is real pages per second and tail latency for Gundam mode at 200 DPI on your GPU. The second is the looping and truncation rate on your own corpus at a 6,144-token budget. The third is whether 5–10 page Base-mode chunks ever beat per-page Gundam on documents where reading order crosses page breaks. If Baidu ships the 128K-context model or the "prefill pool" it describes as future work, revisit the multi-page path. Until then, the per-page job design is the one that scales.
